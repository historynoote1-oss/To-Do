# إدارة الـ Database Migrations

هذا المشروع بيستخدم [Prisma Migrate](https://www.prisma.io/docs/orm/prisma-migrate) بدل
`prisma db push` — عشان يبقى فيه سجل تاريخي (migration history) قابل للمراجعة والـ rollback،
بدل ما كل نشر يعيد مزامنة الـ schema مباشرة على قاعدة البيانات من غير أي أثر.

## ⚠️ حالة انتقالية مؤقتة

- `npm start` دلوقتي بيشغّل `prisma migrate deploy` (الطريقة الرسمية للإنتاج).
- `npm run start:legacy` لسه موجود كـ **fallback مؤقت** بيشغّل `prisma db push` القديمة،
  لدورة نشر واحدة على الأقل، في حالة حصل أي مشكلة غير متوقعة مع تفعيل الـ migrations
  على الإنتاج ومحتجنا رجوع سريع. **المفروض يتشال بعد ما يتأكد استقرار `migrate deploy`
  على الإنتاج لدورة كاملة على الأقل.**

---

## 1. قاعدة العمل للفريق: أي تعديل مستقبلي على `schema.prisma`

من دلوقتي، **ممنوع** تعديل `schema.prisma` وتعمل عليه push مباشرة على أي بيئة (حتى staging).
كل تغيير في الـ schema لازم يمر بالخطوات دي بالترتيب:

1. عدّل `prisma/schema.prisma` بالتغيير المطلوب.
2. شغّل محليًا (على قاعدة بيانات تطوير/staging، **مش إنتاج**):
   ```bash
   npx prisma migrate dev --name <اسم_وصفي_للتغيير>
   ```
   الأمر ده هيعمل حاجتين: (أ) يولّد ملف migration جديد جوه `prisma/migrations/`
   يعكس الفرق بين آخر migration والـ schema الجديد، (ب) يطبّقه فورًا على قاعدة
   بيانات التطوير المحلية عشان تتأكد إنه شغّال صح.
3. راجع محتوى ملف الـ `migration.sql` اللي اتولّد **قبل ما تعمل commit** — تأكد إنه
   بيعمل بالظبط اللي إنت قاصده (خصوصًا لو التغيير بيمس عمود فيه بيانات موجودة).
4. اعمل commit للـ migration الجديدة مع تعديل `schema.prisma` في نفس الـ PR.
5. عند النشر، `prisma migrate deploy` (جوه `npm start`) هيطبّق أي migrations جديدة
   تلقائيًا على قاعدة بيانات الإنتاج بالترتيب — من غير ما يحتاج تدخل يدوي بعد كده.

**ملحوظة مهمة**: `prisma migrate dev` بيُستخدم بس محليًا/على staging. أبدًا مايتشغلش
مباشرة ضد قاعدة بيانات الإنتاج — هو مصمم للتطوير وممكن يعمل reset للبيانات في حالات
معينة (زي drift). الإنتاج بيستخدم `migrate deploy` بس، اللي بيطبّق migrations
موجودة بالفعل من غير ما يولّد أو يغيّر حاجة.

## 2. تفعيل الـ Baseline Migration على قاعدة بيانات الإنتاج (يدوي — معاذ فقط)

### السياق
الـ schema الحالي (`schema.prisma`) مطابق بالفعل لحالة قاعدة بيانات الإنتاج الحالية —
لأنها كانت بتتزامن لحد دلوقتي عن طريق `prisma db push`. يعني **مفيش أي تغيير فعلي
مطلوب على بنية قاعدة بيانات الإنتاج نفسها**. المطلوب بس هو "تعريف" Prisma إن
migration الـ baseline دي متطبقة بالفعل، عشان `prisma migrate deploy` في المرات
الجاية ميحاولش يعيد إنشاء جداول موجودة بالفعل أو يفشل بسبب "drift" بين تاريخ
الـ migrations وحالة القاعدة الفعلية.

### الخطوة المطلوبة (تُنفَّذ يدويًا من معاذ فقط، مرة واحدة)

```bash
npx prisma migrate resolve --applied <اسم_مجلد_الـ_baseline_migration>
```

مثال (استبدل الاسم بالاسم الفعلي اللي هيتولّد، بالصيغة `<timestamp>_baseline`):
```bash
npx prisma migrate resolve --applied 20260725090000_baseline
```

لازم يتشغّل بمتغير `DATABASE_URL` مضبوط على **قاعدة بيانات الإنتاج الفعلية**
(مش staging، مش local).

### إيه اللي بيعمله الأمر ده بالظبط

- **لا يعدّل أي بيانات ولا أي جدول ولا أي عمود في قاعدة البيانات.**
- **لا يشغّل أي SQL من ملف الـ migration نفسه.**
- كل اللي بيعمله: بيكتب سطر جديد في جدول داخلي اسمه `_prisma_migrations`
  (بيتعمل تلقائيًا لو مش موجود) بيقول "الـ migration دي اتعتبرت متطبقة من
  تاريخ النهاردة" — من غير ما ينفّذ محتواها فعليًا.
- ده آمن هنا تحديدًا لأن الـ baseline بالتعريف مطابقة لحالة القاعدة الحالية أصلًا
  (مفيش فرق فعلي يحتاج تنفيذ).

### قبل ما تشغّله

1. اعمل **backup كامل** لقاعدة بيانات الإنتاج (احتياط عام، مش لأن الأمر ده خطر
   في حد ذاته، لكن أي عملية على الإنتاج لازم يكون قبلها backup).
2. تأكد إن `schema.prisma` في الفرع اللي هتنشره فعلاً مطابق لحالة الإنتاج الحالية
   100% (مفيش أي تعديل تاني اتضاف للـ baseline بالغلط).
3. تأكد إن `DATABASE_URL` وقت التشغيل مؤشر فعلاً على قاعدة بيانات الإنتاج مش
   staging بالغلط (والعكس — متشغلوش على إنتاج وانت قاصد تجرب على staging).

### بعد التشغيل

- تأكد إن الأمر رجع رسالة نجاح (`Migration ... marked as applied`).
- بعد كده، `npm start` (يعني `prisma migrate deploy`) هيشتغل عادي في عمليات
  النشر الجاية، وهيطبّق بس أي migrations جديدة اتضافت بعد الـ baseline.

---

## 3. ملخص سريع لدورة النشر الجديدة

| الحالة | الأمر |
|---|---|
| أول نشر بعد إضافة الـ baseline (لسه معاذ ما شغّلش `migrate resolve`) | استخدم `npm run start:legacy` مؤقتًا |
| بعد ما معاذ يشغّل `migrate resolve --applied` يدويًا على الإنتاج (مرة واحدة) | `npm start` العادي (`migrate deploy`) هيشتغل تلقائيًا من غير مشاكل |
| أي migration جديدة بعد كده | تتضاف بـ `prisma migrate dev` محليًا، وتتطبق تلقائيًا عبر `migrate deploy` وقت النشر |
